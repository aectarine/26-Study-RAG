## 1. 프로젝트 목표

Study-RAG의 기본 흐름은 다음과 같습니다.

```text
TXT 문서 업로드
    ↓
문단 단위 청크 분할
    ↓
Ollama 임베딩 생성
    ↓
PostgreSQL + pgvector 저장
    ↓
사용자 질문 임베딩
    ↓
유사 청크 검색
    ↓
필요한 검색 결과를 Ollama에 전달
    ↓
문서 기반 답변 생성
```

현재 목표는 모든 기능을 한 번에 제품 수준으로 완성하는 것이 아니라, RAG의 핵심 구성 요소를 직접 구현하고 검색 결과를 비교·개선하는 것입니다.

## 3. 데이터 구조

대화와 SQL 예시에서 확인된 논리적 테이블은 다음 두 개입니다.

### `source_documents`

업로드된 원본 문서를 관리합니다.

| 필드 | 용도 | 타입·제약조건 |
|---|---|---|
| `id` | 원본 문서 식별자 | 확인 필요 |
| `filename` | 업로드 파일명 | 확인 필요 |
| 기타 메타데이터 | 생성일 등 | 확인 필요 |

### `rag_documents`

원본 문서에서 분리한 청크와 임베딩을 관리합니다.

| 필드 | 용도 | 타입·제약조건 |
|---|---|---|
| `id` | 청크 식별자 | 확인 필요 |
| `content` | 청크 텍스트 | 확인 필요 |
| `embedding` | 벡터 임베딩 | pgvector `vector`로 사용됨, 차원 확인 필요 |
| `source_document_id` | 원본 문서 참조 | 확인 필요 |

검색 쿼리에서는 다음과 같이 원본 파일명과 청크를 연결합니다.

```sql
FROM rag_documents AS r
LEFT JOIN source_documents AS s
  ON r.source_document_id = s.id
```

실제 `CREATE TABLE` 문, 벡터 차원, 인덱스, 외래키 삭제 정책은 코드 또는 마이그레이션 파일을 확인한 뒤 기록해야 합니다.

## 4. 구현 완료 항목

### 문서 관리

- TXT 문서 업로드
- 업로드 문서 목록 조회
- 문서 상세 조회
- 문서 수정
- 문서 삭제
- 업로드된 TXT를 빈 줄 기준의 문단 단위로 분할
- 각 청크의 임베딩 생성 및 저장

정확한 HTTP 메서드와 전체 요청·응답 스키마는 현재 작업 폴더에서 확인할 수 없어 일부 확인이 필요합니다. 대화에서 확인된 업로드 엔드포인트는 다음과 같습니다.

```text
POST /documents/upload
```

### RAG 검색·답변

- 질문 임베딩 생성
- PostgreSQL/pgvector의 코사인 거리 연산자 `<=>`를 이용한 유사 청크 검색
- 검색 청크를 Ollama에 전달해 답변 생성
- 검색 결과가 없을 때 안내 문구 반환
- 응답에 질문, 답변, 출처 청크(`sources`) 포함

검색 SQL의 핵심 형태는 다음과 같습니다.

```sql
SELECT
    r.id,
    r.content,
    r.embedding <=> %s::vector AS distance,
    r.source_document_id,
    s.filename
FROM rag_documents AS r
LEFT JOIN source_documents AS s
    ON r.source_document_id = s.id
ORDER BY distance
LIMIT 3;
```

## 5. 챗 엔드포인트

대화에서 확인된 엔드포인트는 다음과 같습니다.

| 엔드포인트 | 검색·처리 방식 |
|---|---|
| `POST /chat` | 거리순으로 최대 3개 청크를 검색해 답변 생성 |
| `POST /chat/filtered` | `distance <= 0.5`인 검색 결과로 답변 생성 |
| `POST /chat/reranked` | 거리 필터링 후 Ollama가 필요한 청크를 선별해 답변 생성 |
| `POST /chat/deduplicated` | 상위 3개를 가져온 뒤 Python에서 동일한 `content` 제거 |
| `POST /chat/deduplicated-db` | DB에서 동일한 `content`를 먼저 제거한 뒤 거리순 최대 3개 선택 |

기본 요청 형태는 다음과 같습니다.

```json
{
  "question": "ESS 배터리의 적정 운영 온도와 보관 온도를 비교해줘."
}
```

응답의 대표적인 논리 구조는 다음과 같습니다. 정확한 필드 타입과 추가 필드는 확인이 필요합니다.

```json
{
  "question": "질문",
  "answer": "문서 기반 답변",
  "sources": [
    {
      "id": 7,
      "content": "검색된 청크",
      "distance": 0.123,
      "source_document_id": 1,
      "filename": "문서.txt"
    }
  ]
}
```

검색 결과가 없을 때는 다음 안내 문구가 사용된 것으로 확인됩니다.

```text
등록된 문서에서 관련 정보를 찾지 못했습니다.
```

## 6. 검색 방식별 동작

### 기본 검색: `/chat`

질문 임베딩과 가까운 청크를 거리순으로 최대 3개 선택하고 Ollama에 전달합니다.

```text
질문 임베딩 → 거리순 검색 → 최대 3개 선택 → 답변 생성
```

### 거리 필터링: `/chat/filtered`

검색 결과 중 `distance <= 0.5`인 청크만 사용합니다.

```text
질문 임베딩 → 거리순 검색 → distance <= 0.5 → 답변 생성
```

거리 임계값은 관련 없는 결과를 줄이는 데 도움이 되지만, 의미적으로 불필요한 청크를 모두 제거한다고 보장하지는 않습니다. 실제 실험에서 8번 청크도 거리 약 `0.387`로 기준을 통과했지만, 질문에 직접 필요하지 않은 냉각 시스템 정보였습니다.

### 리랭킹: `/chat/reranked`

거리 필터링 결과를 Ollama에 다시 전달해 질문에 필요한 청크를 선별합니다.

```text
질문 임베딩 → 거리 필터링 → Ollama 리랭킹 → 답변 생성
```

리랭킹은 중복 청크를 줄이고 필요한 정보를 선택하는 데 효과를 보였지만, Ollama를 추가로 호출하므로 응답 시간이 크게 증가했습니다. 모델이 항상 중복을 제거하거나 올바른 청크만 고른다고 보장할 수는 없습니다.

### Python 중복 제거: `/chat/deduplicated`

먼저 상위 3개를 검색한 다음, `content.strip()` 값이 같은 청크를 Python에서 제거합니다. DB의 원본 청크는 삭제하지 않습니다.

```text
상위 3개 검색 → content 기준 중복 제거 → 답변 생성
```

이 방식은 구현이 단순하지만, 상위 3개가 중복으로 채워지면 중복 제거 뒤 3개보다 적은 청크만 남습니다.

### DB 중복 제거: `/chat/deduplicated-db`

PostgreSQL의 `DISTINCT ON (r.content)`를 이용해 동일한 내용을 먼저 하나로 줄인 뒤, 바깥 쿼리에서 거리순으로 정렬하고 최대 3개를 선택합니다.

```text
DB에서 content 중복 제거 → 거리순 재정렬 → 최대 3개 선택 → 답변 생성
```

핵심 쿼리 구조는 다음과 같습니다.

```sql
SELECT *
FROM (
    SELECT DISTINCT ON (r.content)
        r.id,
        r.content,
        r.embedding <=> %s::vector AS distance,
        r.source_document_id,
        s.filename
    FROM rag_documents AS r
    LEFT JOIN source_documents AS s
      ON r.source_document_id = s.id
    ORDER BY r.content, distance, r.id
) AS d
ORDER BY d.distance, d.id
LIMIT 3;
```

`DISTINCT ON` 내부는 `content`별로 정렬해야 하므로, 바깥 쿼리에서 다시 거리순 정렬을 해야 전체 결과 중 가까운 청크를 선택할 수 있습니다.

## 7. 실험 문서와 테스트 데이터

검색 품질 비교에는 ESS 배터리 관련 TXT 문서를 사용했습니다. 테스트 문서의 예시 내용은 다음과 같습니다.

```text
ESS 배터리의 적정 운영 온도는 20~25도입니다.

ESS 배터리의 보관 온도는 10~30도입니다.

ESS 배터리 온도가 40도를 초과하면 냉각 시스템을 가동해야 합니다.

ESS 배터리 온도가 0도 미만이면 충전을 제한해야 합니다.

ESS 배터리의 최대 충전량은 85% 이하로 유지해야 합니다.

ESS 배터리의 정기 점검 주기는 30일입니다.
```

이 내용은 RAG 검색 실험용 가상 데이터이며, 실제 ESS 장비 운영 기준으로 사용하면 안 됩니다.

문단 사이의 빈 줄을 기준으로 청크가 분리되므로, 테스트 문서를 만들 때 문단 사이에 빈 줄을 넣었습니다.

또 다른 실행에서는 `/chat`, `/chat/filtered`, `/chat/reranked`의 응답 시간이 각각 6.838초, 3.165초, 27.212초로 측정됐습니다.

### 결과 해석

- 동일한 내용의 청크가 여러 개 존재하면 상위 `LIMIT 3`을 중복 청크가 차지할 수 있습니다.
- Python 중복 제거는 답변에 전달되는 중복을 줄이지만, 제거 후 결과 수가 줄어들 수 있습니다.
- DB 중복 제거 후 `LIMIT 3`을 적용하면 중복이 차지하던 자리를 다음 순위 청크로 채울 수 있습니다.
- 거리 필터링만으로는 질문에 직접 필요하지 않은 의미상 유사한 청크를 완전히 제거하지 못합니다.
- 리랭킹은 필요한 정보를 더 잘 선택한 사례가 있었지만, 추가 Ollama 호출로 느려질 수 있습니다.
- 응답 시간은 실행 시점, Ollama 모델 상태, 캐시 등에 따라 변동하므로 위 단일 실행값으로 일반적인 성능 우열을 확정할 수 없습니다.
- 한 번의 실험만으로 특정 검색 방식이 항상 더 좋은 답변을 만든다고 결론 내릴 수 없습니다.

## 9. 응답 시간 측정

FastAPI 미들웨어를 이용해 API 전체 응답 시간을 측정했습니다. 응답 시간은 실험 비교에 사용했으며, 단계별 시간 측정 코드는 추가하지 않고 기존 미들웨어만 유지하기로 했습니다.

Ollama 리랭킹이 포함된 엔드포인트는 일반 검색보다 느릴 수 있으므로, 품질과 지연 시간 사이의 균형을 확인해야 합니다.

미들웨어의 정확한 로그 형식과 파일 위치는 현재 소스 코드가 없어 확인이 필요합니다.

## 10. 실행 및 Swagger 테스트

실제 프로젝트의 실행 명령은 확인되지 않았습니다. 일반적인 FastAPI 실행 형태는 다음과 같지만, 프로젝트 설정에 맞는지 확인이 필요합니다.

```powershell
uv run uvicorn main:app --reload
```

서버 실행 후 일반적으로 Swagger UI는 다음 주소에서 확인합니다.

```text
http://127.0.0.1:8000/docs
```

단, 애플리케이션 모듈명, 포트, 호스트, API prefix가 다를 수 있으므로 실제 실행 설정을 확인해야 합니다.

### 권장 테스트 순서

1. PostgreSQL/pgvector Docker 컨테이너 실행
2. Ollama 실행 및 프로젝트가 사용하는 모델 준비
3. FastAPI 서버 실행
4. `/docs` 접속
5. `POST /documents/upload`로 TXT 파일 업로드
6. 문서 목록·상세 조회로 원본 문서와 청크 저장 확인
7. `POST /chat`으로 기본 검색 확인
8. 같은 질문을 `/chat/filtered`, `/chat/reranked`, `/chat/deduplicated`, `/chat/deduplicated-db`에 각각 전송
9. `answer`, `sources`, `distance`, `filename`을 비교
10. 응답 시간 로그를 기록

### Swagger 테스트 질문

```json
{
  "question": "ESS 배터리의 적정 운영 온도와 보관 온도를 비교해줘."
}
```

추가로 다음 질문을 사용하면 검색 품질과 환각 여부를 확인할 수 있습니다.

```json
{
  "question": "ESS 배터리를 보관할 때 적절한 온도는 몇 도야?"
}
```

```json
{
  "question": "ESS 배터리의 제조사는 어디야?"
}
```

마지막 질문은 테스트 문서에 답이 없으므로, 모델이 제조사를 임의로 만들어내지 않는지 확인하는 용도입니다.

## 11. 알려진 한계

### 문서 형식

현재 확인된 업로드 형식은 TXT뿐입니다. PDF와 DOCX 텍스트 추출은 아직 구현 또는 검증되지 않았습니다.

### 청크 분할

빈 줄 기준의 문단 분할을 사용합니다. 긴 문단은 지나치게 큰 청크가 될 수 있고, 문맥이 청크 경계에서 끊길 수 있습니다.

### 검색 품질

고정된 거리 기준 `0.5`는 모든 질문과 문서에 적합하지 않을 수 있습니다. 의미가 비슷하지만 직접 필요하지 않은 청크가 남을 수 있습니다.

### 중복 판단

현재 실험의 중복 판단은 정규화된 의미 비교가 아니라 `content` 문자열 기준입니다. 공백·표현이 조금만 달라도 동일한 의미의 청크를 다른 내용으로 볼 수 있습니다.

### 리랭킹 비용

Ollama를 검색 후 다시 호출하므로 품질 개선 가능성이 있는 대신 응답 시간이 증가합니다.

### 답변 신뢰성

검색된 청크가 있어도 모델이 모든 정보를 답변에 반영하지 않을 수 있습니다. 문서에 없는 질문에 대한 거절 정책과 답변 근거 표시가 더 필요합니다.

### 동기 DB 호출 가능성

기존 구현은 `async def` 안에서 동기적인 DB 호출을 사용하는 것으로 설명됐습니다. 실제 코드 확인 전까지는 정확한 여부를 확인 필요로 둡니다. 동기 호출이 맞다면 동시 요청에서 이벤트 루프를 막을 수 있습니다.

### 운영 기능

인증·인가, 파일 크기 제한, 업로드 확장자 검증, 악성 파일 검사, 로깅·모니터링, 자동화 테스트, 배포 설정은 확인되지 않았습니다.

## 12. 향후 작업

현재는 기능을 더 많이 추가하기보다 검색 흐름과 프로젝트 구조를 정리하는 것이 우선입니다.

### 우선순위가 높은 작업

1. 검색 기능 통합
   - 거리 필터링, 중복 제거, 리랭킹을 공통 검색 함수로 통합
   - 기존 비교용 엔드포인트는 실험이 끝날 때까지 유지
   - 최종 통합 API에서 옵션으로 검색 전략 선택

2. 검색 품질 개선
   - `LIMIT`과 거리 임계값을 데이터셋별로 검증
   - 중복 제거 후에도 필요한 청크 수를 확보
   - 질문 유형별 검색 결과 평가
   - 관련성 평가용 테스트 질문과 기대 출처 작성

3. 답변 신뢰성 개선
   - 문서에 근거가 없으면 명시적으로 답변 거절
   - 답변에 출처 문서명과 청크를 표시
   - 검색 결과가 임계값을 넘으면 답변 생성을 생략
   - 답변과 검색 근거가 일치하는지 검증

4. 프로젝트 구조 개선
   - 라우터, 서비스, DB 접근 계층 분리
   - 임베딩·검색·리랭킹·답변 생성 공통 로직 재사용
   - 설정과 환경변수 관리 분리
